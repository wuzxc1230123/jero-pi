# 逻辑原型（单文件 HTML）

把待验证的逻辑——状态机、reducer、纯函数集或小模块——写成**可整体吊走的纯模块**，页面只是壳。一个问题一个文件，双击即跑，可邮件转发，可交给非开发者。

## 页面结构（自上而下）

1. **标题 + 一行说明**：本演示回答什么问题。问题写进可见的引言，不藏在注释里——原型答错了问题就是纯浪费，把问题亮出来让后来者可核对。
2. **当前状态面板**：全相关状态按字段可读渲染（带标签的字段，不是裸 JSON dump），每次点击后重渲染，并高亮刚变化的部分。
3. **自由按钮区**：每个动作一枚按钮，永远全部可点，任何人都能以任意顺序戳这个模型。
4. **引导走查**：每场景一个标签页——场景的一段平实描述（设置什么情境、观察什么）+ 底下有序的**步骤按钮**（点击即执行该步并前进一步）；进入走查先重置到已知初始态，保证每次运行一致。场景选纸上难推理的：快乐路径、刁钻边界、一个应当非法的操作尝试。

## 纯模块纪律

- 逻辑放单个 `<script>`，写成可直接吊进真实代码库的小纯模块：**无 DOM、无 `document`、无事件处理反向流入**——页面调用它，绝不反向。这是原型能活过自身寿命的原因：问题裁决后，验证过的 reducer/状态机/函数集原样吊进真实模块。
- 形状随问题选，不随页面接线方便选：离散事件 + 单值状态 → 纯 reducer（`(state, action) => state`）；"现在哪些操作合法"本身是问题 → 显式状态机；无隐含当前态 → 纯函数集；确需长期内部状态 → 清晰方法面的小类/模块。
- **写给领域专家，不写给代码**：按钮与状态用领域语言（有 GLOSSARY 术语表就用它的词），平实解释正在发生什么。
- 无框架、无构建器、无服务器；一切内联。React 应用或 dev server 都会毁掉"可分享"。
- 克制的美：干净排版、慷慨留白、至多一个强调色；无动画无花活——不跟状态和按钮抢注意力。
- 他们的"等等，这不应该可能"、"我原以为 X 会是另一回事"就是原型的产出——那是**想法里的 bug**，正是本原型的目的。要新动作/新场景就加，原型会演化。

## 反模式

- 给原型写测试——需要测试的原型不是原型。
- 接真实数据库——内存状态，除非问题专门关于持久化。
- 泛化——不写"万一以后要支持 X"；原型只回答一个问题。
- 逻辑与页面糊在一起——纯模块一旦引用 DOM 就不可吊走。
- 把 HTML 壳上线——页面为手动点击优化，值得保留的是背后的逻辑模块。

## 回收

问题裁决后：验证过的纯模块吊进真实模块（决策被吸收）；HTML 壳随全量原型去 `prototype/<name>` 分支留作一手来源，单文件形态在那里永远可以重新打开。
