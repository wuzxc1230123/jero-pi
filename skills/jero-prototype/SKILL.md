# 设计原型

回答一个问题：**这个设计分歧能不能用可运行的代码裁决？** 原型是一次性代码，唯一产出是答案——结论回流 SDD 产物（design 契约 / spec 决策），原型本体全量存 `prototype/<name>` 分支当一手来源，绝不进 main。

## 何时用

- SDD design/proposal 阶段遇到"散文谈不拢"的问题：状态模型对不对、交互流顺不顺、这个界面该长什么样。
- 问题必须**可运行才能回答**——能用引用、计算或既有代码回答的不开原型（那是 explore/research 的事）。
- 在 SDD 会话中经技能解析契约加载（编排器注入路径），独立会话也可直接触发。

## 分支二选一

先判定问题类型，选错分支整个原型白做：

| 问题 | 分支 | 产物 |
|---|---|---|
| "这个状态机/逻辑/数据形状对不对？" | [references/LOGIC.md](references/LOGIC.md) | 单个自包含 HTML，双击即跑 |
| "这个界面应该长什么样？" | [references/UI.md](references/UI.md) | 同一路由 `?variant=` 切换的 3 个结构迥异变体 |

拿不准时看问题贴近哪侧（后端模块 → LOGIC，页面/组件 → UI），并在产物顶部写明所做假设。

## 纪律

1. **一次性，且明确标注**。原型代码放在它服务的模块/页面近旁（上下文一目了然），命名让人一眼看出是原型；遵循项目既有目录约定，不发明新的顶层结构。
2. **一条命令可跑**。UI 原型走项目任务 runner 一条命令启动；逻辑原型是双击即开的单 HTML。启动不需要思考。
3. **默认无持久化**。状态在内存——持久化恰恰是原型要检验的东西，不是它该依赖的东西；问题确实涉及存储时，用带 "PROTOTYPE, wipe me" 名字的草稿库/文件。
4. **零打磨**。不写测试、不做超出"能跑"的错误处理、不抽象。目标是快速学到一件事。
5. **每次操作后暴露完整相关状态**（逻辑）或**每次变体切换呈现整体**（UI），让变化可见。
6. **结论回收，本体归档**。验证过的决策折叠进真实代码或 design 契约；原型全量（含 UI 切换器与落选变体）提交到 `prototype/<name>` 分支——不进 main、不开 PR——并在实现 issue/design 里留指向该分支的指针；答案本身（裁决 + 它解决的问题）写进 design 的对应决策条目。main 只留验证过的决策。

## 与 SDD 的衔接

- design 遇到"纸上谈不拢"的契约问题时，产出原型并裁决；验证过的片段（reducer/状态机/schema/类型形状）回流 `design.md` 契约段——spec 的"不得虚构实现细节"由此获得实证来源。
- 原型**不是 SDD 阶段**：不进 `jero-ai.sdd-status/v2` 状态权威、不产生阶段产物路径、不改变阶段依赖图；它是 design/proposal 的输入侧工具。
