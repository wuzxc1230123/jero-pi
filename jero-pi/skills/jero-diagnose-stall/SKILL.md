# 编排停滞诊断

回答一个问题：**编排为什么停了？** 诊断是只读的——先读事实，再分类，最后给第一步动作；绝不替编排器做状态转移，也绝不绕过任何门。

## 第一步：读事实（不要猜）

按顺序收集，缺哪项就如实说缺哪项：

1. `/jero-sdd-status`——活跃变更、`next_recommended`、首个阻塞；
2. 会话内 SDD 面包屑（最近一次注入的活状态，与 status 是否一致）；
3. `subagent_status` / Agents 视图——是否有未 `agent_settled` 的子代、占用中的队列槽；
4. `/jero:changes`——工作树是否正在等一个评审或交付决策；
5. `/jero:guard` / `/jero:doctor`——环境与权限是否先坏了。

## 第二步：按类别定位

| 停滞类别 | 识别特征 | 第一步动作 |
|---|---|---|
| 状态投影不解析 | status 报畸形/不匹配/变更歧义 | 检查活跃变更是否歧义（多个 changeRoot）、`openspec/config.yaml` 是否在；绝不本地重算或推断状态 |
| 门失败停链 | 同一阶段两轮重跑后自动链停止，报告点名失败门 | 对比两轮失败反馈的差异；同类失败两轮即架构问题信号，不再机械重跑 |
| 等人确认丢失 | 无损分组提示 / consent / `size:exception` / 编辑根请求发出后无下文 | 向用户原样重放提示（选项、后果、允许答案、精确令牌），绝不推断同意或代答 |
| 子代未结算 | 子代已有保留答案但未 `agent_settled`，或队列槽不释放 | 等待结算或取回保留答案作为诊断；绝不为同一变更并行启动第二执行者 |
| 修复循环 | 同一修复连续 3 次失败 | 既定架构问题信号：停止修补，回到 design/proposal 层重新切分工作 |
| 预算停 | 停在 `ask-on-risk`，预测超评审预算（默认 400 行） | 把交付决策（auto-chain / single-pr / size:exception）原样交还用户 |

## 第三步：报告

诊断结论包含：停滞类别（上表之一）、支撑事实（引用读到的具体状态与命令输出）、第一步动作、以及"不做什么"（哪些门绝不绕过）。不属于任何类别时如实报告"未分类"并列出已排除的类别——绝不硬套最近的类别。

## 边界

- 只读诊断：不调用 `/jero-sdd-continue`、不 settle 子代、不代替任何权威做状态转移；
- 诊断结论是散文建议，执行决定归用户与编排器；
- 环境级故障（git / 权限 / 工具链事故）先走编排纪律的事故规则单独诊断，不适用本表。
