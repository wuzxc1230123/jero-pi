# XR 开发（VR/AR，OpenXR）

XR 是 3D 的严格子集外加两套新纪律：**性能预算减半**（VR 双目渲染）
与**舒适度即功能**（晕动是 bug 不是偏好）。4.x 基线走官方 OpenXR：
`XRInterface` + OpenXR runtime（桌面可无头显模拟起步）。

## 场景骨架

- 中心节点 `XROrigin3D`，其下 `XRCamera3D`（头显姿态）与每只手一个
  `XRController3D`（控制器姿态）；世界尺度用真实米制——玩家身高尺度
  错了舒适度直接崩。
- 相机由 XR 系统驱动，**不脚本改 XR 相机姿态**；要"移动玩家"就移动
  Origin。
- 非 XR 构建兼容：XR 分支用 `OS.has_feature("xr")`/接口就绪判定隔离，
  桌面版不带 XR 依赖编译进主流程（参照 `csharp-dotnet.md` 的语言边界
  思路：XR 是模块边界）。

## 舒适度纪律（违反 = 玩家生理不适弃游）

- **相机控制权归玩家**：瞬移（teleport）或平滑转向（可调速）二选一，
  提供选项；绝不脚本夺镜头做"演出运镜"。
- 加速度/视角摇晃最小化；UI 跟头不跟世界（护眼距离 + 视野锚定），
  世界空间 UI 只用于可交互物。
- 交互拾取：控制器 `grab` 事件 + 拾取锚点（物件抓握偏移），碰撞体
  按真实比例；手柄振动反馈接 `godot-game-feel` 的层级思想。

## 性能预算

- VR 单帧预算 = 目标刷新率的一半渲染量（双目）：90Hz VR ≈ 11ms 总
  预算——比 60fps 桌面紧得多；draw call/Lod/光照纪律按 `performance.md`
  再收紧一档。
- 注视点渲染/动态分辨率按 runtime 能力开；移动 XR（一体机）再降档。
- 物理与逻辑 tick 与渲染解耦（固定步长，`physics-gameplay.md`）——
  XR 帧率波动大，固定步长保手感一致。

## 测试策略

- 桌面 OpenXR 模拟器起步：骨架/交互逻辑先跑通（无头显迭代快）。
- **舒适度只能真机人测**：模拟器通过 ≠ 不晕；发布前真机清单走查
  （移动/转向/拾取/UI 阅读距离）——自动化为零，冒烟清单代替
  （`verification.md` 的"跑起来看一眼"在 XR 语境=真人戴机走查）。
- 多 runtime 差异（SteamVR/Meta/一体机）：目标 runtime 矩阵真机各过
  一遍，别只测一家。

## NEVER

- **NEVER 脚本驱动 XR 相机姿态**（晕动直通车）——要移动玩家移 Origin。
- **NEVER 桌面模拟通过就宣布舒适度 OK**——生理反馈只有真人能测。
- **NEVER 桌面级渲染预算做 VR**（双目成本 × 一体机量级）——立项就
  按 XR 预算做减法。
- **NEVER XR 代码散进核心逻辑不分层**：XR 是模块边界，桌面构建不带
  XR 路径。
