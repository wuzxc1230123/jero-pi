# Jam 与快速原型工作流

目标：**可玩的核心循环 > 完整的系统**。时间盒内只做减法能赢的事。

## 范围裁剪（开工前 1 小时定死）

- 一句话循环："玩家反复做 X 因为 Y"。写下来贴住；与循环无关的想法进 `ideas-later.md` 不实现。
- 系统清单 ≤3 个（参考 `genres-recipes.md` 对应类型的最小清单再砍一半）。
- 内容量钉死：1 关/1 敌/1 机制（procgen 项目：1 个生成器无变体）。
- 明确不做的：设置界面、多语言、手柄适配、教程关（jam 版用开头一行字替代）、存档（除非循环需要）。

## 原型纪律（工程面）

- 灰盒先行：色块精灵/CSG/占位音频；`genres-recipes.md` 的选型表直接抄节点结构。
- 通用玩家控制器模板复用（`physics-gameplay.md` 配方 + `game-feel.md` 默认参数），不重写——原型时间花在**循环验证**不花在移动手感从零发明。
- 脚本不抽象：jam 代码允许丑（巨型玩家脚本 OK），但**信号/场景边界纪律不放松**（`signals-groups.md`）——jam 后要不要续命取决于边界是否还在。
- 每 2–3 小时出一次可玩 build（`F5` 玩一遍）——"能跑的丑"随时存在，bug 当场暴露不积压。

## 验证回路（压缩版三道门）

见 `verification.md`；jam 版映射：

1. **每 2–3 小时**：编辑器跑通核心循环（人工，60 秒内一遍）。
2. **每晚**：`godot --headless --path . --import` + parse 检查（退出码绿才算当天收工——脚本名打错当场显形）。
3. **提交前**：真实导出目标平台一次并启动（`export-publishing.md` 命令行节）——jam 死法之首是最后一小时导出失败（模板缺失/纹理选项/字体丢失）。

- 玩家可见改动截图留证（1 张/功能），收尾剪 trailer 直接用。

## 团队分工（多人 jam）

- 内容/代码/美术并行：数值与内容走 `.tres`（`resources-data.md`）——美术与策划不碰代码文件，合并零冲突。
- 主干短分支：每功能一晚合入，冲突当天清；场景文件冲突 = 两人改同一场景（开工分场景所有权）。

## 收尾与提交（最后 25% 时间）

- 冻结新功能（只修阻断 + 体验打磨一档：`game-feel.md` L0/L1 反馈全补上——jam 评审对 juice 极敏感）。
- 出包清单：目标平台导出 + 干净机启动一次 + itch 上传（`butler push`，`export-publishing.md` itch 节）+ 页面（截图 3 张/说明 3 行/操作方式）。
- 已知问题写在页面（崩溃规避法）——jam 评分对"说明诚实"宽容，对"打开就崩"零容忍。

## Jam 后续命决策（一周内）

- 留：核心循环被陌生人玩住了（留存证据：试玩者的自发重开次数）。
- 重构优先级：补测试（`testing.md`——原型零测试）→ 拆场景边界 → 抽数值进 Resource → 再谈加内容。
- 弃：循环需"再做一个系统才好玩"的——那是新游戏不是迭代，开新仓不背债。

## 红线

- 最后一小时改引擎版本/升级依赖（导出即炸）。
- 无导出验证的"完成"。
- 教程/开场动画占掉最后半天（玩家 30 秒内必须摸到核心循环）。
